# STATUS: состояние кода и результатов

Обновляется после каждого этапа. Последнее обновление: закрытие этапа 3 (реальная трасса Azure Functions
2021, проверка воспроизводимости, локальный коммит). Отчёт пишется в другом чате; этот чат только для кода.

**Это симуляция на Python, не реальный Kubernetes-кластер. Нагрузка синтетическая (этапы 1-2) и реальная
трасса Azure Functions 2021 с искусственным масштабированием (этап 3).**
Все числа считаются кодом; в этом файле числа только как ориентир (источник указан), при
расхождении верны файлы в `results\`.

## 3. Как запускать (из C:\NIR, порядок важен)

```bash
pip install -r requirements.txt
python experiments/train_forecasters.py        # обучение моделей, ~25 мин (можно по частям: ar lstm gru lstm2 gru2)
python experiments/calibrate_fallback.py       # порог fallback для каждой модели на валидации (сиды 2000+)
python experiments/run_experiments.py          # 7 профилей x 10 сидов x 17 конфигураций, ~1-2 мин
python experiments/analyze.py                  # таблицы, статистика, гипотезы, графики
python experiments/pareto.py                   # кривые "потери - под-секунды" (равная стоимость)
python experiments/pareto_stats.py             # парные тесты при равной стоимости
python experiments/sensitivity.py              # чувствительность к времени запуска пода T_start
python experiments/diagnose_forecast.py        # где прогнозист выигрывает/проигрывает (валидация)
python experiments/smoke_baselines.py S3       # быстрая проверка симулятора на одном профиле
python experiments/inspect_trace.py            # обзор реальной трассы Azure Functions 2021 (нужен data\*.txt)
# этап 3 (реальная трасса), порядок важен:
python experiments/trace_train.py ar lstm2 gru2  # ~1 ч (LSTM ~30 мин, GRU ~60 мин; можно по отдельности в параллель)
python experiments/trace_run.py calibrate        # порог fallback по валидационным окнам
python experiments/trace_run.py run              # 135 тестовых окон x 13 конфигураций + развёртка параметров, ~8 мин
python experiments/trace_analyze.py              # таблицы, бутстрэп по окнам, равная стоимость, устойчивость по третям, H2, графики
python experiments/trace_sensitivity.py          # чувствительность на трассе к масштабу K и T_start, ~5 мин
```

Как читать код: `sim/cluster.py` - класс `Simulator.run()` (цикл по секундам),
`pab_step()` (логика ПАБ: N*, упреждающий запуск, fallback), `hpa_step()` (реактивный HPA),
`distribute_lc()` (взвешенный Least Connections). `forecast/models.py` - `NNForecaster2`
(нейросеть v2), `_loss` (асимметричная потеря). `experiments/run_experiments.py` - список
конфигураций `CONFIGS` и функция `work()` (один профиль и сид).

## 4. Параметры (источник: `SimParams` в sim/cluster.py и README)

Под: μ = 50 запросов/с, очередь 100, запуск 30 с, прогрев 20 с (холодный под 30 %). HPA: период 15 с,
цель 70 %, допуск 10 %, окно вниз 120 с, метрика с задержкой 10 с. ПАБ: шаг 5 с, горизонт 12 бинов
(60 с), ρ = 0,7, выдержка вниз 60 с, разгон веса 20 с. Прогон 1800 с. Сиды: обучение 1000+,
валидация 2000-2009, тест 0-9.

Конфигурации: A1 RR+фикс., A2 RR+HPA, A3 LC+HPA (основная база), A4 агрессивный HPA, A5 HPA цель
50 %, A6 быстрый HPA; B1/B2 LSTM/GRU v1, B3 AR, B4 только масштабирование, B5 без fallback,
B6 naive, B7 линейный тренд, **B8 LSTM v2 (основной вариант)**, B9 GRU v2, B10, B11 абляции.

## 6. Что не получилось / ограничения / открытое

- Польза именно нейросетевого прогноза над «последним значением» **статистически не доказана**.
- Fallback при сдвиге распределения (S5X) не помог: потери без него ниже (B11 против B8).
  Гипотеза H3 в исходной формулировке не подтверждается.
- Ступенчатые всплески непредсказуемы по истории (диагностика): ~120 с нарушений SLO остаются у всех.
- Профиль S6 и версия v2 выбраны после просмотра первых результатов (на валидации, не на тесте).
- Метрики `burst_detect` и `lead_s` на S5 неинформативны (перекрытие всплесков).
- Признаки прогноза только rps и sin/cos времени; SARIMA/Prophet нет (вместо них AR-Ridge).
- **Реальная трасса (этап 3).** Azure Functions 2021 (Zhang et al., SOSP 2021, CC-BY), файл
  `data\AzureFunctionsInvocationTraceForTwoWeeksJan2021.txt` (305 МБ, 1 980 951 вызов, 119 приложений,
  14 дней; в git не кладётся; скачивается с https://github.com/Azure/AzurePublicDataset, файл
  `data/AzureFunctionsInvocationTraceForTwoWeeksJan2021.rar`, 18,4 МБ, распаковывается 7-Zip).
  Издатель указывает, что временные метки изменены; нагрузка serverless; средняя интенсивность 1,64 запр/с
  (масштабируется в K = 29,4 раза по обучающим суткам, 99-й перцентиль 5-секундных бинов -> 400 запр/с).
  Правила заданы до просмотра результатов (`sim/trace.py`): окна 30 мин в реальном времени без отбора,
  672 окна, хронологически 403 обучение / 134 валидация / 135 тест; единица наблюдения - окно, ДИ бутстрэпом
  по окнам (окна коррелированы).
  Отступления от плана и неудобные факты:
  - сетка параметров запаса (ρ от 0,3, цель HPA от 0,25) **расширена после первого просмотра**, потому что
    исходная сетка не покрывала стоимость A6; это не подбор под результат, но надо оговаривать;
  - у 10 % тестовых окон пик выше 913 запр/с, у одного 2359 при пределе кластера 2000 запр/с (перегрузка
    неизбежна для любого метода); поэтому результаты даны и для "допустимых" окон (пик <= 1600 запр/с);
  - порог fallback на трассе 0,6-0,8 (ошибка прогноза большая: sMAPE ~75 %), модели учились на 401 из 403
    окон (отбор окон почти ничего не отсеял);
  - валидационная потеря на трассе 0,55 против 0,21 на синтетике (трасса намного "рванее");
  - GRU учится вдвое дольше LSTM и чуть хуже; v1-модели на трассе не обучались;
  - вторая трасса (Huawei Private 2023, rps по секундам, Google Drive) не использована.
- `git`: репозиторий инициализирован в C:\NIR, `origin` = https://github.com/Jesspern/load_balancer.git,
  коммитов и push нет (только по вашей команде).

## 7. Ориентир по числам на реальной трассе (источники: `results/trace/*.csv`, `tables.md`)

Основной прогон, 135 тестовых окон (потери пулированные [95 % ДИ бутстрэпом]; под-секунд на окно):
A3 4,39 % [3,16; 5,77], 5443; A6 2,31 %, 8474; B6 (naive) 3,55 %, 6479; B3 (AR) 3,02 %, 6406;
**B8 (LSTM v2) 2,76 % [2,01; 3,49], 6592**; B9 (GRU v2) 2,84 %, 6787; B11 (без fallback) 2,62 %, 7008.
B8 против A3: потери -1,63 п.п. [-2,61; -0,70], но +1149 под-секунд на окно (+21 %).
Равная стоимость (потери семейства при бюджете, равном стоимости B8 / A6; допустимые окна): LSTM v2 против
HPA: -0,65 п.п. [-1,04; -0,29] / -0,53 п.п. [-0,95; -0,21] (значимо); на всех окнах при бюджете B8
-0,63 п.п. [-1,42; +0,18] (не значимо), при бюджете A6 -0,66 п.п. [-1,25; -0,14] (значимо).
LSTM v2 против ПАБ-naive при равной стоимости: -0,67 п.п. [-1,11; -0,23] (значимо). ПАБ-naive против HPA:
разницы нет. LSTM против AR и GRU: не значимо. MAE прогноза почти одинаковый у всех моделей (25-28 запр/с),
доля недооценок: LSTM 0,26, naive 0,49.
Дополнительные базы без обучения (B12 = пик за последние 30 с, B13 = среднее + std за 60 с) и уточнение вывода:
при равной стоимости LSTM v2 значимо лучше "наивного" (-0,67 п.п. [-1,10; -0,31]) и "пика за 30 с"
(-0,70 п.п. [-1,07; -0,35]), но **не значимо** лучше "среднее + std" (-0,14 п.п. [-0,41; +0,11]) и AR
(-0,16 п.п. [-0,57; +0,16]) (бюджет B8, все окна). Сама эвристика "среднее + std" против HPA при равной
стоимости: -0,48 п.п. (на допустимых окнах значимо). Значит, выигрыш прогнозного управления на трассе
обеспечивает прогноз с запасом на изменчивость; **польза именно нейросети над простой эвристикой не доказана**.
B8 против B12 (пик за 30 с) в основном режиме: потери 2,76 % против 3,09 % при меньшей стоимости
(6592 против 7058 под-секунд).

Устойчивость (`trace/thirds.csv`): B8 против A3 по потерям лучше во всех трёх третях тестового периода
(-0,9, -2,7, -1,0 п.п., ДИ не содержат 0), стоимость выше на 930-1290 под-секунд на окно.
Чувствительность (`trace/sensitivity.csv`, модели не переобучались): B8 лучше A3 при p99 нагрузки 200/400/800 запр/с
(-1,5/-1,6/-1,3 п.п.) и при T_start 10/30/60 с (-1,7/-1,6/-1,3 п.п.), ДИ не содержат 0; A6 всегда даёт меньше
потерь, но тратит на 30-65 % больше под-секунд.
**H2 на трассе (8 спокойных окон, пик <= 150 запр/с):** B8 тратит на 21,5 % больше под-секунд, чем A3
(порог 15 %), то есть по стоимости **не выполнено**; p95 лучше (0,10 с против 0,18 с), потерь нет. Окон мало.

**Вывод по трассе противоположен синтетике лишь частично:** на синтетике выигрыш объяснялся быстрой реакцией
(naive не хуже LSTM), на трассе naive при равной стоимости не лучше HPA, и нужен прогноз с запасом
(LSTM, AR, среднее + std).

## 8. Воспроизводимость (проверено)

Заново прогнаны `run_experiments`, `analyze`, `pareto`, `pareto_stats`, `trace_run run`, `trace_analyze` на уже
обученных моделях: все итоговые таблицы, статистика и гипотезы совпали побитово с предыдущим прогоном.
Исключения, которые надо знать:
1. `runs.csv` и `pareto_runs.csv` содержат колонку `arrived`, добавленную в метрики после первых прогонов;
   остальные колонки идентичны.
2. Обучение нейросетей (`train_forecasters.py`, `trace_train.py`, около 1,5 ч) заново не запускалось. Сиды заданы,
   но на многопоточном CPU веса могут чуть отличаться, поэтому файлы `forecast/*.pt` (в git не входят)
   считаются частью результата.
3. `sensitivity.py` и `trace_sensitivity.py` в проверку не входили.

Не входит в git: `data/` (трасса, 305 МБ), `forecast/*.pt`, `results/cache/`, старые и новые версии отчёта,
файл переноса контекста между чатами, локальная защита от удаления.
